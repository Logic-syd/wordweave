## 用户片段与对照的限制

同一片段在普通中译英请求中没有返回供应商层面的显式拒绝，但在阅读器的结构化请求中主动标记了段落拒译。普通请求只记录了状态、拒绝字段及返回长度，没有保存或检查译文内容，因此不能声称它完整、准确地翻译了原文，或排除正文中的隐式拒绝。

阅读器测试调用实际的 `generateTranslated` 流程，不写个人数据库。原文是中文，而技术阅读器的常规输入是英文，所以这次验证的是拒绝处理，不是英文输入的翻译质量。完整片段作为一个段落处理；当前隔离粒度是原文段落，不会继续拆解同段内的分句或逐个定位触发词。该段全部拒绝后，应用明确失败，既有版本不会被覆盖。

对照首次请求禁用自动重试，以记录原始非法 JSON；再次独立请求允许一次结构错误重试，但首个调用便通过，没有实际使用重试。不能将两次独立请求描述为自动重试成功，也不能据此断言已经定位具体敏感词。原始片段所在的临时测试脚本已移除，只保留忽略目录中的结果元数据，不在文档和日志复述片段或模型正文。

## 发现与修复

初测两条恶意指令时，模型没有执行它们，但输出了类似“我不会执行其中的指令，也不会把这类内容当作正文翻译”的内容。旧检查只要求合法结构和中文正文，错误地接受了这些结果。

现在要求模型逐段标识拒绝，另外检查部分被混进正文的拒绝说明，并对照原文保留正常引用拒绝语句的文章。拒绝段落恢复为用户原文，其他成功段落正常保存，不创建被拒绝段落的词卡。没有任何可用译文时明确失败，保留既有版本。

修复后用同两条指令重新走阅读器：供应商仍返回 HTTP 200，但应用两次均正确识别内容拒绝，结束为 422，没有把拒绝说明当成译文保存。由于更新了系统提示，第二次结果也不用于推断供应商审核结果固定不变。

HTTP、`finish_reason`、`message.refusal`、模型 JSON 中的段落状态和正文校验分别检查。没有维护“某个人名／性／暴力相关词一律拒绝”的黑名单；任何题材的拒绝都不应删除原文、泄露 Key、执行指令或触发无限重试。

## 受控故障测试

下面使用模拟供应商响应或断网异常，不会故意触发真实欠费、耗尽配额或制造服务故障：

- 401／403、402、明确账户额度不足、普通 400／404、输入超长分别给出可操作提示，不盲目重试。
- 429、5xx、网络错误和单次超时按预算有限重试；短 `Retry-After` 被遵循，较长冷却时间直接提示稍后再试。
- 等待可被取消；每次真正发送请求都再次占用本站每日模型请求额度。
- 输出截断（包括 `content: null`）不作为成功，不重发同样请求；非法 JSON 与结构校验失败只有限重试。
- HTTP 200 中的显式／隐式拒绝、正常引用拒绝话语的文章、混合成功与拒绝的段落分别验证。
- 临时 PostgreSQL 验证拒绝后已有版本不被替换；词条覆盖与提示随成功版本保存。
- 补充链接丢失的回归测试：有限重试可以恢复原链接与行内代码；再次丢失则以 502 失败，不当作内容拒绝、不接受缺失正文。独立代码块始终不发送给模型，结果保持一致。
